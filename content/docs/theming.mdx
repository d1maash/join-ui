Everything visual in Joinway UI resolves through CSS custom properties. Change a
token and every component follows — including the ones already installed in your
project.

## The principle

The system has two layers, and they follow different rules. The chrome —
navigation, sidebar, buttons, documentation type, code blocks, catalog cards —
is achromatic. Every one of its colour tokens is declared in `oklch` with a
chroma of exactly zero, so the frame can only ever render in black, white and
the grey ramp between them.

The components are the exception, and it is deliberate. They are the product
rather than the frame, so they carry hue: a status chip, a progress marker, a
chart series. They read it from four semantic families — `--info`,
`--positive`, `--caution` and `--critical` — never from a literal colour, which
is what keeps a component retintable in one place and consistent with the ones
beside it. A hard-coded hex is still a bug.

Inside the chrome the older discipline holds, and it is the more durable one.
Meaning there is carried by weight, rule thickness, size and spacing. A
destructive control in the interface is not red; it is the one control set in
inverted ink. A warning is not amber; it is an aside with a thicker left rule,
an icon, and the word spelled out.

Two consequences are worth stating up front, because they are what most people
expect to find and will not:

- There are no gradients in the system and no elevation tokens. Depth is drawn
  with hairlines, not with shadow.
- `--radius` is `0rem` and every step of the chrome radius scale resolves to
  zero. Site surfaces have square corners; components round through the
  separate `rounded-soft*` scale below.

## The grey ramp

The ramp is the whole of the chrome's palette. Twelve steps, from paper to ink,
and every achromatic token below is an alias onto one of them.

```css title="app/globals.css"
:root,
.light {
  --grey-0: oklch(1 0 0);
  --grey-50: oklch(0.975 0 0);
  --grey-100: oklch(0.95 0 0);
  --grey-200: oklch(0.9 0 0);
  --grey-300: oklch(0.82 0 0);
  --grey-400: oklch(0.68 0 0);
  --grey-500: oklch(0.55 0 0);
  --grey-600: oklch(0.44 0 0);
  --grey-700: oklch(0.32 0 0);
  --grey-800: oklch(0.22 0 0);
  --grey-900: oklch(0.13 0 0);
  --grey-1000: oklch(0 0 0);
}
```

In `oklch` the first component is perceptual lightness, so the steps are evenly
spaced to the eye rather than evenly spaced in bytes. Dark mode inverts the
ramp — `--grey-0` becomes black, `--grey-1000` becomes white — which is why the
semantic layer below barely changes between themes. See
[dark mode](/docs/dark-mode).

## Semantic tokens

Nothing outside this block should reference `--grey-*` directly. Components read
the semantic names, so retuning the ramp retunes the whole interface.

```css title="app/globals.css"
:root,
.light {
  /* Surfaces */
  --background: var(--grey-0);
  --foreground: var(--grey-1000);
  --card: var(--grey-0);
  --card-foreground: var(--grey-1000);
  --popover: var(--grey-0);
  --popover-foreground: var(--grey-1000);
  --muted: var(--grey-100);
  --muted-foreground: var(--grey-600);
  --subtle: var(--grey-50);

  /* Rules. `--border` is the hairline; `--border-strong` is the ink rule. */
  --border: var(--grey-200);
  --border-strong: var(--grey-1000);
  --input: var(--grey-300);
  --ring: var(--grey-1000);

  /* Emphasis. Inverted ink is the only "accent" the system has. */
  --primary: var(--grey-1000);
  --primary-foreground: var(--grey-0);
  --primary-soft: var(--grey-100);
  --accent: var(--grey-1000);
  --accent-foreground: var(--grey-0);
  --accent-soft: var(--grey-100);
  --secondary: var(--grey-100);
  --secondary-foreground: var(--grey-1000);

  /* Status — achromatic by design. See below. */
  --destructive: var(--grey-1000);
  --destructive-foreground: var(--grey-0);
  --success: var(--grey-700);
  --warning: var(--grey-700);

  --code-bg: var(--grey-50);
  --selection: oklch(0 0 0 / 0.14);

  /* Shape — the chrome is square. Swiss grids do not round their corners. */
  --radius: 0rem;

  /* Motion */
  --duration-instant: 80ms;
  --duration-fast: 140ms;
  --duration-base: 200ms;
  --duration-slow: 320ms;
  --ease-out-soft: cubic-bezier(0.22, 1, 0.36, 1);
  --ease-in-out-soft: cubic-bezier(0.65, 0, 0.35, 1);
}
```

Then map them onto utilities with `@theme inline` — see
[Tailwind setup](/docs/tailwind-setup).

## The component palette

Four families carry hue, and each is three tokens with the same shape. `--X` is
the ink: a solid fill, and the colour of text and icons sitting on the tint.
`--X-soft` is that tint, used as a background. `--X-foreground` is whatever sits
on top of the solid `--X` fill.

```css title="app/globals.css"
:root,
.light {
  --info: oklch(0.5 0.17 253); /* in progress, informational */
  --info-soft: oklch(0.965 0.022 253);
  --info-foreground: oklch(0.99 0.005 253);
  /* …and the same three for --positive, --caution and --critical. */
}
```

`--positive` is green and reads as success or complete, `--caution` is amber and
reads as a warning, `--critical` is red and covers error, blocked, and anything
destructive happening inside a component. The pre-existing `--destructive`,
`--success` and `--warning` tokens are unchanged and still achromatic — they
belong to the chrome, and a component should reach for the families instead.

Every family is declared twice, once in `:root, .light` and once in `.dark`, so
a component never needs a `dark:` variant to pick the right hue. That is not
housekeeping: it is what keeps the per-preview theme islands working, and it
remains a hard rule. See [dark mode](/docs/dark-mode).

All twelve are registered in `@theme inline`, so they arrive as ordinary
utilities:

```tsx
<span className="inline-flex items-center gap-1.5 rounded-soft-sm bg-info-soft px-2 py-1 text-info">
  <Loader2 aria-hidden="true" className="size-3.5" />
  In progress
</span>
```

## Token reference

| Token | Purpose |
| --- | --- |
| `--grey-0` … `--grey-1000` | The ramp. Every achromatic token aliases onto it |
| `--background` / `--foreground` | Page surface and body text |
| `--card` / `--card-foreground` | Panel surfaces, bounded by a rule rather than raised |
| `--popover` / `--popover-foreground` | Floating surfaces — menus, dialogs |
| `--muted` / `--muted-foreground` | Recessed fill and secondary text |
| `--subtle` | The quietest fill; asides, table zebra, code chrome |
| `--border` | Structural hairline |
| `--border-strong` | Ink rule for emphasis, hover and selected states |
| `--input` | Form control boundary |
| `--ring` | Focus outline |
| `--primary` / `--primary-foreground` | Inverted-ink emphasis; the primary action |
| `--primary-soft` | Flat fill for a selected or held state |
| `--secondary` / `--secondary-foreground` | Quiet fill with normal ink on top |
| `--destructive` / `--success` / `--warning` | Chrome status, achromatic |
| `--info` / `--info-soft` / `--info-foreground` | Component hue: in progress, informational |
| `--positive` / `--positive-soft` / `--positive-foreground` | Component hue: success, complete |
| `--caution` / `--caution-soft` / `--caution-foreground` | Component hue: warning |
| `--critical` / `--critical-soft` / `--critical-foreground` | Component hue: error, blocked, destructive |
| `--code-bg` | Code block and inline code fill |
| `--selection` | Text selection wash, the one token using alpha |
| `--radius` | Base radius for the chrome. `0rem`; the derived scale is zero throughout |
| `--radius-soft-sm` / `--radius-soft` / `--radius-soft-lg` | The component radius scale — a tag, a control, a card |
| `--duration-*` / `--ease-*` | Motion timing |

## Status without colour

`--destructive`, `--success` and `--warning` belong to the chrome and are
deliberately achromatic. They resolve to ink and to `--grey-700`, which means
they are indistinguishable from each other on luminance alone in some contexts.
That is intentional, and it carries one hard requirement:

<Callout variant="warning">
  A status token is never sufficient on its own. Pair it with an icon **and** a
  spelled-out text label. Anything that would have relied on red-versus-green to
  communicate must communicate in words instead.
</Callout>

A component using `--critical` or `--positive` is under exactly the same
obligation. The hue is an accelerator, not the message: a chip in
`--critical-soft` and one in `--positive-soft` differ by hue and very little
else, and the component layer no longer removes the option of getting this
wrong the way the chrome's palette does. WCAG 1.4.1 is satisfied by the glyph
and the label, never by the fill. So a component that renders a state draws it
with a glyph and spells it out, and uses weight, an ink rule or a tint to raise
its priority:

```tsx
<p className="flex items-center gap-2 text-foreground">
  <AlertTriangle aria-hidden="true" className="size-4" />
  <span className="font-medium">Payment failed</span>
</p>
```

## Shape and motion

The chrome has one shape token and it is zero:

```css
:root {
  --radius: 0rem;
}
```

The Tailwind scale (`--radius-xs` through `--radius-3xl`) is pinned to zero as
well, so `rounded-lg` on a site surface is a no-op rather than a surprise.
Components round through a scale of their own — `--radius-soft-sm` for a tag,
`--radius-soft` for a control and `--radius-soft-lg` for a card, reached as
`rounded-soft-sm`, `rounded-soft` and `rounded-soft-lg`. `rounded-full` is left
alone in both layers, because a pip or an avatar is a circle rather than a
rounded rectangle.

Durations and easings are tokens for the same reason colours are — so timing
stays consistent across components you installed months apart:

```tsx
className="transition-colors duration-[var(--duration-fast)] ease-[var(--ease-out-soft)]"
```

## Retuning the ramp

Rebranding the chrome is not a hue change; there is no hue in it. It is a change
of contrast and of where the greys sit. Edit the ramp, leave the semantic layer
alone, and every surface moves with it:

```css title="app/globals.css"
:root {
  /* A softer ramp: paper instead of white, graphite instead of black. */
  --grey-0: oklch(0.98 0 0);
  --grey-1000: oklch(0.18 0 0);
  --grey-200: oklch(0.88 0 0);
  --grey-600: oklch(0.46 0 0);
}
```

<Callout variant="tip">
  Keep the ramp achromatic. Retinting belongs to the component layer instead:
  override `--info`, `--positive`, `--caution` and `--critical` — with their
  `-soft` and `-foreground` partners, in both themes — and leave the greys
  alone. Re-check every contrast pair after either kind of change, because a
  tint is almost never as light as it looks.
</Callout>

## Scoped themes

Tokens are inherited custom properties, so any subtree can override them. This
is a supported pattern, not a hack — inverting a section is a token swap:

```tsx
<section
  style={{
    "--background": "var(--grey-1000)",
    "--foreground": "var(--grey-0)",
    "--border": "var(--grey-700)",
  } as React.CSSProperties}
>
  <YourComponent>Inverted panel</YourComponent>
</section>
```

The same mechanism powers the theme switch on every preview — see
[dark mode](/docs/dark-mode).

## Component-level overrides

Every component merges `className` last through `cn`, so `twMerge` resolves the
conflict in your favour:

```tsx
<YourComponent className="border-border-strong bg-subtle p-8" />
```

Where a component owns more than one surface, it exposes a second class hook
rather than making you fight selectors:

```tsx
<YourComponent className="border-border-strong" innerClassName="bg-subtle p-8" />
```

## Contrast

The ramp is built around pure black on pure white, so the headline pairs are at
the top of the scale in both themes:

| Pair | Light | Dark |
| --- | --- | --- |
| `--foreground` on `--background` | 21:1 | 21:1 |
| `--primary-foreground` on `--primary` | 21:1 | 21:1 |
| `--muted-foreground` on `--background` | 7.8:1 | 7.3:1 |
| `--muted-foreground` on `--muted` | 6.7:1 | 6.9:1 |

`--muted-foreground` is the one to watch. It carries most of the body copy and
it is the token people lighten first when a page feels heavy; it has roughly
three steps of headroom above 4.5:1 and no more.

Note what the rules are and are not doing. `--border-strong` and `--ring` are
pure ink, so any boundary that has to be perceivable — focus rings, selected
states, the outline of a control — clears 3:1 with room to spare. `--border` is
a structural hairline at around 1.3:1 and is not trying to meet that threshold.
Where a boundary is the only thing identifying an interactive control, reach for
`--border-strong`.
